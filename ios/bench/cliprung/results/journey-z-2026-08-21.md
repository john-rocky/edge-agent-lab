# cliprung — the z acceptance rule (background-corpus calibration)

Same harness, same video, same 11 queries as `journey-2026-08-21.md`. The
question is the one that file left open: the cosine has no absolute scale, so
is there a *relative* one that decides presence?

    z = (peak_in_video − mean_background) / stddev_background

run: `DEVELOPER_DIR=/Applications/Xcode-27.0.0-Beta.5.app/Contents/Developer \
swift run -c release cliprung --video ~/Desktop/journey.mp4`

Everything the earlier file measured re-ran unchanged in this run — every
cosine, every rate, every rendered sentence is byte-identical; only the
graph-warmup timing line moved (11.2 → 58.6 ms/frame on a cold first run). The
z sections are added beside the old ones, not in place of them.

## the background set

211 clips, 422 frames — 2 frames per clip, at 30% and 70% of each clip's
duration. Manifest committed at `background/null-corpus.txt`; the frame
embeddings are derived data and are cached at `.build/background-embeds.bin`,
which is gitignored (the source clips' licence forbids redistributing the
mp4s, and 844 KB of float32 is not repo content).

Source: `~/code/what-can-ai-see/clips` — the wcas benchmark's field tier, 581
clips carrying a `clip.mp4`, grouping into 48 first-token categories. The
manifest takes up to 5 per category, spread evenly through each category's
sorted order rather than taking the first 5, so the 49-clip smoke-fire family
contributes five different fires and not five degradations of one. None of
journey.mp4's four Pexels sources (2675512 / 4729779 / 853936 / 28320907)
appears in the corpus — checked by id.

**Is it a fair null?** Two answers, and they differ.

- **Size: yes, comfortably.** Halving it to 211 frames (1 per clip) leaves
  every rate in every sweep below identical. Individual z values move by at
  most 0.156 (sunset 5.422 → 5.578) and by ~0.05 typically. A few hundred
  frames is already past the point where the estimate's size matters — but
  0.05–0.16 is the resolution of this instrument, and one comparison below
  turns out to sit inside it.
- **Composition: biased, and the bias is load-bearing.** wcas is a
  workplace/anomaly benchmark — warehouse, conveyor, PPE, retail, kitchen,
  office, plus outdoor entry/exit, vehicles, animals and crowds. journey.mp4 is
  outdoor travel footage. The null contains many people and no ocean, beach,
  forest path or skyline. That asymmetry is exactly why the rule works here and
  exactly the limit of it: see the last section.

## verdict

**No z cut reaches 8/8 with 0 false positives.** The exact boundaries, read off
the z column:

- a cut in **(2.090, 2.362]** → **8/8 with 1 FP** (the cat);
- a cut in **(2.773, 3.925]** → **6/8 with 0 FP**;
- and a cut in **(2.757, 2.773]** → 7/8 with 0 FP, which is a **0.016-wide
  window** and must not be counted. Halving the null moves a single z by up to
  0.156; this window is a tenth of that. It is the same knife edge the
  incumbent stands on, found in new units, and calling it an operating point
  would be reading noise.

**But z dominates the cosine at every operating point that is wide enough to
name.**

| false positives allowed | best cosine cut | best z cut |
|---|---|---|
| 0 of 3 | 4/8 (cosine 0.265–0.278) | **6/8** (z 2.77–3.93) |
| 1 of 3 | 6/8 (cosine 0.247–0.265) | **8/8** (z 2.09–2.36) |
| 2 of 3 | 8/8 (cosine 0.199–0.232) | 8/8 (z 0.94–2.09) |

And the separation is qualitatively different, which is the real result:

- **In cosine units** the true hits span 0.232–0.329 and the false ones
  0.199–0.265. **Five** of the eight true hits sit inside the false range.
- **In z units** the true hits span 2.362–6.012 and the false ones 0.940–2.757.
  **One** of the eight true hits sits inside the false range.

The two false positives the old file blamed on the missing scale are gone. "A
person walking away" — 0.265 in cosine, above five true hits — is 2.09 in z,
below all eight. "Snow" is 0.94. The diagnosis in canon was right, and the fix
it implies works on exactly the failures it predicted.

**What survives is not a scale failure.** The single remaining overlap is "a
cat" at z 2.757, scoring on the beach scene that contains a puppy — the case the
playbook already records both rungs failing identically (`VNRecognizeAnimals`
fires `cat` there too, and CLIP scores "a cat" 0.247 against its own "dog"
0.242). No calibration can fix a model that finds a puppy cat-like; only a
verification frame can. So the acceptance rule remains impossible, for a
narrower and more honest reason than "the numbers do not separate".

**Robustness of the operating point.** The incumbent's 0.27 sits inside
(0.265, 0.278] — a 0.013-wide band, 13% of the width its true hits span, with a
false positive 0.005 below it. The z rule's 0-FP band is (2.773, 3.925], 1.15
wide, 32% of its own hit spread. The incumbent is not wrong on this footage; it
is narrow on this footage, and it was chosen by sweeping this footage.

**Against the incumbent, plainly: equal where it ships, better where it does
not.** In the shipped labels-first union, z ≥ 2.5–3.5 measures 8/8 with 1 FP —
the same 8/8 with 1 FP the incumbent measures, and the FP is arm A's cat in both
cases. On this footage the change is invisible in the shipped configuration,
because labels answer 6 of 8 and the two they miss are the two highest cosines
(0.329, 0.285) — the easiest possible work for the CLIP rung. Standalone, where
labels are silent more often, z is better: 6/8 against 4/8 at zero false
positives, and 8/8 against 6/8 at one.

**Recommendation: do not change the app on this evidence.** z buys no measured
point in the configuration that ships, costs a 422 KB asset that must ship with
it, and the case for it rests on margin rather than on a rate. The time to
adopt it is a second footage set where the label shelf goes silent on more than
two of eight queries — then the standalone number is the one that ships, and
6/8-at-0-FP against 4/8-at-0-FP is a real difference. Recorded, not built.

## cost, if it is ever adopted

- **Ships with the app.** Queries are free text, so per-query null statistics
  cannot be precomputed; the background *frame embeddings* have to be on the
  device. 422 × 512 float32 = **844 KB**, or **422 KB at float16**, next to the
  CLIP bundle's own 305 MB. Halving the null to 211 frames costs nothing
  measurable (above) and halves that again.
- **Query time: negligible.** 422 dot products of 512 floats = 216K
  multiply-adds, plus a mean and a variance. The video's own 25 frames are 12K.
  Both are far below one frame of CLIP encoding (~11 ms warm), so the null adds
  no perceptible latency to a search.
- **Index time: unchanged.** The null is computed once, offline. Building this
  one took 13.5 s to decode 422 frames and 3.2 s to embed them.

## what this rests on

One video, four scenes, 11 queries, **3 negatives**. Every false-positive rate
in this file is a fraction of three. The z numbers are stable to halving the
null and the ranking result reproduces the earlier run exactly, but no rate
here should be read as a rate.

And one limit the corpus makes visible: **the null can only calibrate a query
whose subject it has seen.** "A person walking away" is refused because the
background is full of people — its background mean, 0.210, is the highest of
the eleven. A null with no people in it would have given that query a low mean,
a high z, and a false positive. "Snow" is refused for the opposite and safer
reason: the background has no snow either, but journey.mp4's peak for snow is
barely above the corpus mean, so nothing inflates. The rule is therefore only
as good as the null's coverage of what users ask about, which is an open-ended
set. That is a second reason not to ship it as a presence decision.
